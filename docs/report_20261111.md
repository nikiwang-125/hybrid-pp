# 本周进展汇报（2026-11-11）：混合模型流水线建模与方案搜索

环境：Nemotron-Nano-9B-v2，vLLM 0.10.1.1 V0，双机 PP=4（slave21 + slave20，4×RTX 3090），万兆网络。
详细材料：`docs/reconfig_comm_20261111.md`（显存/重配置/通信）、`docs/modeling_20261111.md`（计算模型/模拟/搜索/验证）。

## 一句话结论

**傍晚补充（更重要）**：
1. 开 graph 后瓶颈是 vLLM 主进程单核 CPU（GPU 利用率约 25%）。V0 的 SPMD 模式在混合模型 + PP 下有 bug（漏传 finished_requests_ids 与 virtual_engine），插件修复后吞吐 1K +39%、8K +45%（各 3 次，t>10），串行/并发输出 7/7 一致；1K TTFT 变差 13%。
2. CUDA graph 重录 95% 是 gc.collect：录制期间跳过 GC，PP=4 每段重录 7–14 s → 0.4 s，输出 7/7 一致。
3. CUDA 虚拟内存部分收缩 KV（让出 844 MiB）约 54 ms，KV 地址不变、保留数据完好、已录 graph 可直接回放。
4. 开 graph 后默认均分即最优；chunk 2048 默认最优。
详见 modeling_20261111.md 第 10–16 节。

**下午补充（最重要）**：长输入慢的主因是 vLLM 超过 8192 token 关掉 CUDA graph。把 `--max-seq-len-to-capture` 设为 max_model_len 后，8K 输入吞吐 +21%、16K +13%（各重复 3 次，显著），输出与原来一致（6/7 逐字相同，1 条思考文字差一词、答案相同），无额外显存或启动代价；此时默认均分即最优，推荐切分的优势消失（见 modeling_20261111.md 第 9 节）。


建立了“计算 + 显存 + 通信 + 流水线”的初版闭环。单段计算模型对新切分误差 ≤5%。
实测发现最优切分会随负载变化，但收益只有 4–6%。一次布局切换仅 CUDA graph 重捕获就要 7–14 s，整个引擎重启要 60 s，而 decode 每段约 8 ms 的非 GPU 开销比 GPU 计算本身还大。
**建议下一阶段优先降低每步 CPU/通信开销、改进调度，而不是先做在线布局切换。**

## 重配置成本基线（单卡，移 3 层）

| 操作 | 耗时 |
|---|---|
| 释放 / 重建 KV 池 | ~6 ms / ~7 ms |
| 加载 3 层权重（pinned 内存 / safetensors 热缓存） | 14–47 ms / 200–350 ms |
| 在途状态迁到另一 GPU（attention 1.5 GiB / Mamba 0.5 GiB） | 155 ms / 48 ms |
| 跨机迁移 1.5 GiB（按 1.18 GB/s 推算） | ~1.3 s |
| **CUDA graph 重新捕获（PP=4，每段 20 个 graph，各段并行）** | **7–14 s** |
| vLLM sleep / wake（只释放恢复，KV 内容丢失，约 1 GiB 常驻） | 0.95 s / 0.74 s |
| 整个引擎重启 | ~60 s（其中显存 profiling 26 s） |

## 回答计划中的问题

- **瓶颈是否随负载变化？** 是。短输入（graph 模式）时每段非 GPU 开销主导，默认均分最好；长输入（>8192，退回 eager）时 **rank0 的 eager decode 比其他段慢 2–3 倍**（推测与引擎同进程的 CPU 竞争），减轻第一段的切分 TPOT 快 6–7.5%。16K + chunked prefill 下同样成立（7,17,18,14：TPOT −6.2%，吞吐 +3%；18,10,10,18：吞吐 −6.5%）。
- **模型能否指导新方案？** 能给出绝对量级，并对长输入推荐了实测更好的方案；但切分间差异（5–8%）与模型误差同量级，排序可靠性有限（秩相关 0.04–0.71）。
- **哪类负载存在切分收益？** 本次只有长输入（8192:128）有可测收益：TPOT −7.5%，吞吐约 +5%（统计上仅为倾向）。
- **一次布局切换的成本？** 释放/重建 KV 毫秒级，权重与状态搬运百毫秒到秒级，但 KV 重建后 CUDA graph 失效，**重捕获约 7–14 s**，是主项；整引擎重启约 60 s。
- **下一阶段优先做什么？** 证据倾向先做动态调度和降低每步开销，布局切换暂缓，除非能找到收益更大的负载（如更长上下文、chunked prefill 场景）。

## 已知问题与边界

1. TTFT 预测偏低（长输入 −26%），prefill 阶段有未建模开销；需加入 micro-batch 标识后拆分等待与传输。
2. 模型把切分间差异放大了约 2 倍，推测是把非 GPU 开销当作串行占用，实际上与 GPU 计算部分重叠。
3. 推荐方案与默认已各重复 3–4 次；其他切分仍只有 1 次。长输入单次吞吐波动约 3%，TTFT 约 6%。
4. 只覆盖一个模型、PP=4、两种负载、并发 16、无 chunked prefill；graph 重捕获时间取自启动日志，未在运行中单独触发测量。
5. sleep 测试进程退出时 segfault（数据已写出），原因待查。
6. 模拟器未建模 chunked prefill 的 mixed 步；16K 负载只有实测，每个切分 1 次。
7. rank0 CPU 竞争是推测，需用 CPU 绑核或 CPU 占用测量验证。

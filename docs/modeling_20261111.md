# 计算模型、流水线模拟与切分搜索（2026-11-11）

代码：`hybrid_pp/pipeline_sim.py`（fit / search）。数据：`results/part_sweep_20261111/`（7 切分 × 2 负载，双机 PP=4）。
模型与逐 run 对照：`results/part_sweep_20261111/sim_model.json`；搜索结果：`search.json`。

## 1. 实验设置

- 双机 PP=4（rank0/1 在 slave21，rank2/3 在 slave20，1→2 边界跨机），graph 模式，`HYBRID_PP_PROFILE_LAYERS=0`（只记整步，避免逐层插桩开销）。
- max_model_len 16384（因此 **chunked prefill 关闭**，已在 server.log 确认），max_num_seqs 16，并发 16，32 条请求；负载 1024:128 与 8192:128。
- 切分（attention 在第 14/21/30/39 层）：default(14×4)、18,10,10,18、16,12,12,16、12,16,16,12、20,12,12,12、12,12,12,20 为训练；**15,13,15,13 在拟合前预留为验证**，未参与任何拟合或调参。
- 每个 trace 跳过前 2 步作为热身。

## 2. 阶段计算模型

按阶段内各类层数量做线性回归，所有阶段、所有切分共享一组系数，因此能给没跑过的切分定价：

- decode：t = c0 + Σ_T n_T·(a_T + b_T·batch) + n_attn·g·ctx_sum + embed/lm_head 项
- prefill：t = c0 + Σ_T n_T·(a_T + b_T·tokens) + n_attn·g·Σlen² + embed/lm_head 项
- 目标值为 GPU span（`total_ms`）。CPU `exec_ms` 不可用：graph 模式下非末段在 launch 后约 1 ms 就返回。
- decode 分 graph / eager 两个模型。**V0 中任一序列长度 > 8192（`max_seq_len_to_capture`）整步退回 eager**，每段慢 2–4 倍；8192 输入的负载 decode 基本都是 eager。

| 阶段级误差（中位数） | 训练 | 留出切分 15,13,15,13 |
|---|---:|---:|
| decode graph | 1.3% | 1.1% |
| decode eager | 4.4% | 4.9% |
| prefill | 0.7% | 0.7% |

## 3. 显存模型校准

`capacity.py` 权重估计与 stage_mem 日志实测在全部 rank 上相差 ≤ 0.01 GiB。运行时额外部分（激活峰值 + non-torch）实测 3.7–4.0 + 0.13 GiB/段，由启动时按 max_num_batched_tokens = 16384 的 profiling 决定，已作为搜索默认值（4.15 GiB）。
V0 的 KV 池按各段最小空余决定：18,10,10,18 两端段权重 6.86 GiB，KV 预算 10.17 GiB；中间段 12.6 GiB。当前负载下 6545 种切分全部装得下，显存不是本负载的约束。

## 4. 流水线模拟器

事件驱动模拟 V0 语义：PP 个 VE 各自 scheduler，新请求分到未完成请求最少的 VE；每个 VE 同时只有 1 个 micro-batch 在流水线中；每段 FIFO 独占；无 chunked prefill 时一步为纯 prefill 或纯 decode；闭环客户端固定并发；边界通信用第 4 步的通信模型。
唯一校准常数：**每段非 GPU 开销 8.0 ms**（仅用训练切分的 TPOT 网格搜索得到）。与 trace 一致：decode 每段 CPU call 8–12 ms，而 GPU 只有 5–7 ms。

端到端（留出切分）：

| 负载 | 吞吐 预测/实测 | TTFT 中位 预测/实测 | TPOT 中位 预测/实测 |
|---|---:|---:|---:|
| 1024:128 | 215.1 / 218.3（−1.5%） | 1386 / 1495 ms（−7.3%） | 63.9 / 61.8 ms（+3.4%） |
| 8192:128 | 60.9 / 56.2（+8.4%） | 7738 / 10517 ms（−26%） | 199.1 / 203.6 ms（−2.2%） |

## 5. 证据边界（重要）

1. **实测切分间差异很小**：同负载下 7 种切分吞吐差 5–8%，TPOT 差 6–8%。
2. **模型能预测绝对量级，但还不能可靠地给切分排序**：预测与实测的 Spearman 秩相关 0.04–0.71；模型把切分间差异放大到 10–19%。原因推测：把每段 8 ms 非 GPU 开销当作串行占用，而实际上它与其他段 GPU 计算部分重叠，使不均衡切分的实际损失小于模型预测。
3. **TTFT 系统性偏低**（长输入 −26%）：prefill 阶段有未建模的开销。用 step 编号对齐跨段记录时结果自相矛盾（多 VE 交错导致同一 step 号不一定是同一 micro-batch），需在 trace 中加入 micro-batch 唯一标识后才能拆分等待与传输。
4. 只有一个模型、PP=4、两种负载、并发 16；未覆盖 chunked prefill（max_model_len > 32K）。

## 6. 切分搜索

枚举每段 ≥ 6 层的全部 6545 种连续切分 → 容量模型筛选（全部通过）→ 最慢段粗筛 → 前 8 名加两个基线做完整模拟。
预测第一名 7,17,18,14：8192:128 吞吐 63.6 vs 默认 61.8（+3%），1024:128 与默认持平。该差异在模型误差范围内，且第一段 7 层超出训练范围（12–20 层），属于外推。已安排实测验证（见第 7 节）。

## 7. 实测验证

`results/validate_20261111/`：推荐方案 7,17,18,14 与 default 重测，同配置。

| 指标 | 7,17,18,14 实测 | 模型预测 | default 重测 | default 上午 | default 两次差（噪声） |
|---|---:|---:|---:|---:|---:|
| 1024:128 吞吐 tok/s | 207.7 | 209.6 | 220.7 | 222.1 | 0.6% |
| 1024:128 TPOT 中位 | 65.3 ms | 65.0 | 60.1 | 60.7 | 1.0% |
| 8192:128 吞吐 tok/s | **59.9** | 63.6 | 57.9 | 57.1 | 1.5% |
| 8192:128 TPOT 中位 | **182.9 ms** | 182.9 | 192.1 | 199.0 | 3.5% |
| 8192:128 TTFT 中位 | 10.6 s | 8.8 s | 11.1 s | 9.9 s | 12% |

结论：
- **长输入（8192:128）推荐方案优于默认**：吞吐 +3.4~4.9%，TPOT −4.8~8%，均超过同条件重复噪声；TPOT 预测与实测一致。
- **短输入（1024:128）推荐方案劣于默认约 6%**，模型预测两者持平，未预测出该差距。
- 因此**最优切分随负载变化**，但收益量级为 4–6%。对照重配置成本（权重搬运与状态迁移百毫秒至秒级，另需重建 CUDA graph；整引擎重启约 60 s），目前证据不支持优先做在线布局切换。
- TTFT 单次实测重复差 12%，比较 TTFT 需多次重复。

## 8. 长输入 + chunked prefill（16384:128，max_model_len 40000）

`results/long_20261111/`。max_model_len > 32K，vLLM 自动开启 chunked prefill（已在 server.log 确认：`chunked_prefill_enabled=True`，`max_num_batched_tokens=2048`），出现 prefill chunk 与 decode 混合的 mixed 步。序列 > 8192，**所有步都是 eager**。每个切分只测 1 次。

| 切分 | 吞吐 tok/s | TTFT 中位 | TPOT 中位 |
|---|---:|---:|---:|
| default 14×4 | 43.1 | 7.2 s | 305.2 ms |
| 7,17,18,14 | 44.4（+3.0%） | 8.5 s（+18%） | 286.3 ms（−6.2%） |
| 18,10,10,18 | 40.3（−6.5%） | 8.1 s（+12%） | 326.4 ms（+7.0%） |

各段 GPU 忙碌时间（秒，跳过前 2 步；decode / mixed / prefill）：

| 切分 | pp0 | pp1 | pp2 | pp3 |
|---|---|---|---|---|
| default | **41.0** / 33.3 / 8.4 | 14.6 / 31.4 / 7.9 | 14.8 / 31.1 / 7.9 | 16.0 / 31.1 / 7.9 |
| 7,17,18,14 | **26.9** / 18.9 / 5.9 | 13.8 / **38.9** / 9.2 | 14.1 / **40.1** / 9.4 | 13.5 / 31.2 / 7.9 |
| 18,10,10,18 | **45.5** / 41.7 / 9.9 | 12.5 / 23.4 / 6.4 | 11.7 / 22.1 / 6.3 | 19.3 / 40.2 / 9.5 |

**新发现：rank0 的 eager decode 异常慢。** default 四段层数相同，pp0 decode 却是其他段的 2.8 倍；7,17,18,14 的 pp0 只有 7 层，仍比 14 层的 pp3 慢一倍。推测原因：rank0 的 worker 与 vLLM 引擎（调度、输出处理、API server）在同一进程/主机 CPU 上，eager 模式每个 kernel 都需 CPU 发射，CPU 竞争直接拉长 GPU span。graph 模式发射开销小，所以短输入时该效应弱。
这解释了为什么"第一段少放层"的方案只在 eager 主导的长输入上有效，而在 graph 主导的短输入上反而更差（中间段变重）。也说明**瓶颈不只来自层的计算量，还来自 rank0 的 CPU 竞争**。待验证：把 driver 与 rank0 分到不同 CPU 核，或测 rank0 的 CPU 占用。

其他：
- 7,17,18,14 把负载移到 pp1/pp2 后，mixed 步变成 pp1/pp2 最重（39–40 s），TTFT 变差 18%（单次测量，TTFT 波动约 6%，此差距可能是真的，需重复）。
- 当前模拟器**未建模 chunked prefill 的 mixed 步**，因此本节只有实测，没有预测。

## 9. 放宽 CUDA graph 长度上限（`--max-seq-len-to-capture = max_model_len`）

原因：V0 录 graph 时地址表按 `max_seq_len_to_capture`（默认 8192）定长分配（`worker/model_runner.py:1008-1019`），`_use_captured_graph` 要求 batch 内最长序列不超过该值（`:743-751`），否则整步 eager。混合模型只有 4 层 attention 用地址表，但整模型一起退回 eager。
数据：`results/capture16k_20261111/`、`results/capture40k_20261111/`，每组 1 次。所有纯 decode 步都改为 graph（之前全 eager）。

| 负载 | 切分 | 上限 8192（基线） | 上限 = max_model_len | 变化 |
|---|---|---:|---:|---:|
| 8192:128 | default | 58.2 tok/s，TPOT 195.6 ms（n=4 均值） | 72.5 tok/s，TPOT 145.5 ms | 吞吐 +25%，TPOT −26% |
| 8192:128 | 7,17,18,14 | 61.2，181.1（n=3） | 62.8，164.6 | +3% |
| 16384:128 | default | 43.1，305.2（n=1） | 48.2，270.1 | 吞吐 +12%，TPOT −11% |
| 16384:128 | 7,17,18,14 | 44.4，286.3（n=1） | 43.9，291.9 | 持平 |

- graph 捕获时间（7–9 s/段）、graph 显存（0.06–0.10 GiB）与 KV 预算均不变，未见代价。
- 段 1 decode GPU 忙碌时间降到与其他段相当（8K default：7.4 / 6.7 / 6.5 / 8.1 s；此前 16K eager 为 41 / 15 / 15 / 16 s），支持“rank0 慢源于 eager 下的 CPU 发射竞争”。
- 开 graph 后默认均分在两种长输入上都优于推荐切分（−13% / −9%）：第 7–8 节中推荐切分在长输入的优势是 eager 回退造成的，不是层分布本身的收益。
- 16K 提升较小：chunked prefill 下的 mixed 步仍不走 graph。
- 第 2–6 节的模型和搜索均在默认上限下拟合，放宽上限后需重新测量与拟合。

### 9.1 重复测量与正确性（补测）

重复：`results/capture_rep{1,2}_20261111/`、`results/long_base_rep{1,2}_20261111/`。默认均分，Welch t 检验。

|---|---|---:|---:|---:|---:|
| 8192:128 | 吞吐 tok/s | 58.2±2.0（n=4） | 70.7±3.0（n=3） | +21.4% | 6.3 |
| 8192:128 | TPOT 中位 ms | 195.6±4.5 | 147.9±5.3 | −24.4% | −12.6 |

| 16384:128 | TTFT 中位 ms | 7288±75 | 7291±29 | 0.0% | 0.1 |

TTFT 不变符合预期：prefill 本就不走 graph。

正确性（`hybrid_pp/graph_correctness.py`；`results/graph_correctness_20261111/`、`results/graph_correctness_long_20261111/`）：PP=4 默认均分，两种上限各起一次服务，greedy、逐条发送。3 条短提示 + 4 条 9760/11949/13063/15255 token 的检索题（在长列表中找 3 个柜号的密码）。
- max_tokens 64：7/7 逐字一致（模型先输出 `<think>`，未写到答案）。
- max_tokens 400：6/7 逐字一致；1 条（11949 token）前 975 字符相同后，思考文字中 “data” 变为 “records”，最终答案相同。检索正确率两者完全相同（2/3、2/3、3/3、2/3），错误答案也相同，属模型能力而非配置问题。
- 结论：放宽上限不改变计算结果；唯一差异是 graph 与 eager 内核的浮点差异在近似并列的 token 上被 greedy 放大，属正常现象。
